# Workspace file governance

Use this skill at the start of experiments, scripting, implementation, and other tasks likely to create, import, move, or reorganize workspace files, even when the user does not mention file management. Read the root `AGENTS.md` and directory table and rules in `README.md` as the workspace authority; use `workspace-doc-governance` for related documentation and requirement updates.

## Decide placement

Identify each item's purpose, origin, owner, lifecycle, deployment role, sensitivity, and whether it may be committed. Choose the existing directory matching those facts before writing. Distinguish deployable package code, experiments, project documentation, external references, original materials, datasets, model weights, and temporary outputs. Do not infer that an external resource is redistributable; record known origin, version and license, and mark unknowns. Do not add runtime dependencies on lab, references or datasets. Create a directory only for a distinct role and update its owning directory description.

Do not reference local paths outside this workspace in scripts or non-root documentation, or load or execute external script files. When external source code is needed, first establish origin and permission, copy the necessary code to its appropriate workspace location and maintain an independent adaptation. Resolve user-supplied script paths and symlinks before loading. Installed interpreters, programs and libraries are not external script files; source attribution links and workspace-relative references remain valid.

Before creating a file, infer its role from the user's task and call `python .agents/skills/workspace-file-governance/scripts/check_layout.py --suggest <kind> [--task <id>]` for an applicable role. Kinds are `training-script`, `training-config`, `training-test`, `inference-script`, `inference-config`, `inference-test` (each requires an ID in `config/perception_tasks.json`), `shared-core`, `package-test`, `navigation`, `integration`, `repo-tool`, and `temporary`. Dataset roles (`dataset-script`, `dataset-config`, `dataset-annotation`, `dataset-sample`, `dataset-export`, `dataset-shared-script`, `dataset-shared-annotation`) and `ros-package` are delegated to `config/workspace_layout.yaml` via `lab/scripts/contracts/workspace_layout.py`. Shared inference belongs in the existing `aec_vision` core even when developed during an experiment; the experiment's driver and evaluation stay in `lab/`. For external materials, use `README.md` and the relevant owner; for a new dataset task, add it to `config/workspace_layout.yaml` rather than inventing a directory. If intent cannot be inferred, report the missing information; do not guess.

Top-level, dataset-task, feature-branch and ROS-package structure is defined in `config/workspace_layout.yaml`. For dataset and ROS package paths, use `python lab/scripts/contracts/workspace_layout.py suggest --role <role> --task <id>` and `python lab/scripts/contracts/workspace_layout.py check`; the tool checks directory names and declared files only. The root README directory table and the dataset tree/table in `docs/DATASET_DESIGN.md` are generated by `python lab/scripts/contracts/sync_layout_docs.py`; edit the contract, not the generated blocks.

Object classes, parents, owners, authorities, versioning, mutability and lifecycle are defined in `config/workspace_ontology.yaml`; check with `python lab/scripts/contracts/workspace_ontology.py --check`. Add a new object by choosing its parent class and owner, not by creating a synonymous directory or version-named folder.

Check the resulting filename with `python .agents/skills/workspace-file-governance/scripts/check_layout.py --path <relative-path>`. An OK result only means no encoded rule matched. A local-only output is a review warning rather than a forbidden destination, but must not be committed. Run without `--path` for an audit, and with `--staged` to check staged changes and remaining files in affected packages. Exit 0 means no mechanically detected violations, 1 means violations, and 2 means the check could not complete. Review warnings and explain unresolved cases. The local Git hook runs the staged check if `core.hooksPath` is configured as `.githooks`; hooks can be disabled or bypassed and are not a security boundary.

The checker inspects path names, not file contents or semantic correctness. Its default scan covers tracked and non-ignored untracked files plus top-level directories; it does not traverse ignored data, secrets, model or temporary trees, and does not detect all runtime dependencies, ignored files or misplaced but plausible files. Staged symlinks and submodules are flagged for review; their contents and targets are not inspected by the staged check. It never moves or deletes anything. An agent must still inspect task-specific ownership and references.

`workspace_layout.py` is the structural checker: it reads `config/workspace_layout.yaml`, checks declared directory names and files, and checks dataset task/shared roots when `datasets/raw` or `datasets/annotated` exists. It does not read data contents. `check_layout.py` remains the commit-path checker and does not traverse ignored data.

## V4 dataset locations

For V4, use datasets/exports/<task>/{train,test,val} for the single current dataset, datasets/samples/<task>/ for the single current sample, and datasets/scripts/<task>/ for the task's dataset and sample generation entry scripts. Each task keeps config/dataset.yaml for its goals and states and config/source.yaml for its source scope; task generators must consume their own source configuration. Required config files, optional plan files, conditional exceptions and annotation roots are declared in `datasets.tasks.<id>`; include `production_plan.json` or its declared conditional exception. Put genuinely shared capabilities such as Bayesian allocation and perspective operations in datasets/scripts/common/, which may hold sub-packages, and keep task-specific logic within its task. Keep provenance in the existing records; use Git for code history instead of creating parallel version-named output directories. Remove erroneous or expired outputs when authorized, after checking ownership, references and the exact target. Preserve runs/<task>/runs/ and V3 models and records in place: do not delete, move, rename or modify them. Production remains paused until the user explicitly resumes it. Existing scripts may still use older paths; verify and update actual consumers before treating these locations as enforced.

The contract is the authority for task paths, required config files and annotation roots. `datasets/annotated/<task>/` is not a universal rule: a task may declare shared or legacy annotation roots (for example building_name_paper uses `datasets/annotated/fire/` and `datasets/annotated/site_capture_20261112/`; waste_sticker uses `datasets/annotated/waste_bin/`). Run `python lab/scripts/contracts/workspace_layout.py check --task <id>` before producing a task's sample or dataset.

### Review and judgment records

Candidate review runs from datasets/scripts/common/review/ (sampling, geometry, emptiness, masks, overlays, templates, judge, evidence, schema, perspective, cli) plus the per-task datasets/scripts/<task>/config/review_plan.json. Review is a cross-task capability: it screens parent sources and supplies yaw/perspective reference for every task, so its observations live under datasets/annotated/common/, not under one task. Review output splits by whether a later run can rebuild it:

- datasets/scripts/<task>/config/review_selection.json is tracked and holds decisions for the most recent batch: verdict ready/unknown or evidence-backed excluded, role, ground polygon or keypoint region, existing targets, near-duplicate group, reason codes, evidence pointer and code hash. Review and manual writers must merge-preserve untouched prior entries, candidates, annotations, review decisions and reviewer data; a rerun must not default to replacing the whole file. Default validation is read-only and must not rewrite review or manual content. Rebuilding from a template requires an explicit request, detection of existing non-empty manual content, and a recoverable backup first. No plan compiler or task generator consumes this file yet; production_plan.json remains the derived quota/strata plan. Verdicts are automatic, the visual-review method and acceptance criteria are undecided, `accepted_by` stays empty until the user confirms, and the ground-clearance thresholds exist with default 0 (disabled) until an obstacle-ratio limit is set.
- datasets/annotated/common/review/<task>/<batch>/ holds metrics.jsonl, optional overlays/ and manifest.json; datasets/annotated/common/perspective/<task>/<batch>.json holds the exported ground/horizon templates. These are recomputable from raw media plus code and parameters, and hold no media copies.

datasets/annotated/ is gitignored, so it may only hold recomputable observation and candidate material. A decision that cannot be recomputed belongs under datasets/scripts/<task>/config/ and must not exist only inside the ignored tree. Review entries stay pending until judged; unknown is a first-class verdict, no threshold may promote an unresolved frame to ready, and target absence is proven per frame rather than inherited from a sibling frame. Keep `source_available`, `annotated`, `candidate`, `auto_validated`, `human_confirmed`, and `training_admitted` as independent counts; every summary reports all six plus pending. Automatic review can add only `auto_validated`, and an empty `accepted_by` remains pending rather than rejected. Human semantic decisions and box/keypoint/mask decisions use separate fields and evidence.

### Stores and legacy assets

query_cache.sqlite3 under datasets/annotated/media_index/ is a rebuildable query view, production_state.sqlite3 in the same directory holds durable generation receipts, and datasets/blender_source_registry.sqlite3 is the authoritative Blender asset registry maintained by lab/scripts/blender/blender_source_registry.py. training_packages/ is a rebuildable distribution copy and never the authority for a dataset. datasets/assets/ holds blender/ and person/; person/ was moved from datasets/person on 2026-11-15, its 1,334 files are size-identical to datasets/raw/person/teammate_submission_20261110 (not a separate capture), and it carries 281 background frames, 1,001 synth images, reports, 20 artwork files and 7 old scripts as a read-only candidate source, so do not write new generated output there. Do not create version-named output directories, use exports/ as scratch space, or keep a second tracked copy of judgments that already live in the ignored tree.

## Archive and lifecycle ownership

For obsolete authored plans, preserve still-valid facts in their current owner and use Git for prior document history. Update active inbound links and generator inputs; do not leave active duplicate advice. Technical iteration archives exclude documents. Raw inputs, current experiment evidence and user assets retain their own lifecycle. Runtime images/video belong to the configured run output area; memory release, temporary-file disposal and retention of required original evidence are separate operations.

For project-owned Blender assets, use `datasets/assets/blender/` as the central location: `shared/` and task folders hold source models, task working copies, experimental branches, and unresolved backups; `batch_scenes/<task>/<batch>/` holds editable snapshots tied to an existing export batch. Read current Blender asset state from datasets/blender_source_registry.sqlite3 with lab/scripts/blender/blender_source_registry.py; the directory alone does not establish status. Keep the registry updated with evidence references and prior path aliases. Original manifests remain generation-time evidence, not current lifecycle authority. Keep rendered images, labels, and batch manifests in their existing dataset batch directories. Put evidence-backed retired or superseded iterations in `Archive/technical/`; keep disposable Blender test fixtures in `tmp/` and do not treat them as production sources or durable archives. Before moving a scene, check script/config/manifest references, preserve the old-to-current path relation, and verify the moved file and dependencies.

The Blender registry is a catalog snapshot, not a filesystem monitor. For a current inventory, inspect the scoped `.blend` and `.blend1` paths on disk and compare them with registry records; report the covered roots and file types. A registry row alone does not establish that a binary currently exists, and a filesystem scan alone does not establish lifecycle status or provenance.

Classify reviewed assets by evidence and lifecycle: shared-scene candidate, task working copy, task model source, experiment branch, automatic backup/possible orphan pending review, or retired version. A current path reference establishes use, not quality or universal authority. Byte-identical copies can still serve a required task path; do not delete them until generator and manifest dependencies and edit lifecycle are settled. Treat `.blend1` as a prior-save candidate, not disposable clutter, until unique recovery value is checked. Retire a version only after checking inbound references and recording its lifecycle status.

Distinguish active consumer references from historical manifest records when assessing lifecycle. For ignored, untracked binary assets, Git references and documentation do not restore the asset contents; record that recovery boundary explicitly.

Resolve ordinary placement from existing directory ownership and proceed. A checker error must be resolved before placing or staging the affected file; a review warning needs a purpose/ownership check and can be resolved from existing evidence. A new path alone does not require permission. An OK result still requires checking content and runtime dependencies relevant to the task.

## Change and inspect

- Inspect Git status first and preserve unrelated or uncommitted work. Search actual consumers, paths, imports, launch/config references, scripts, generators, tests and docs before moving anything. Consider relative path resolution, platform case sensitivity and deploy packaging.
- Move only items whose ownership and destination are established and whose relocation is within the user's task. Repair references and relevant documentation together. Preserve external originals and user data; do not move or delete unknown, sensitive or ignored files just to make the tree tidy.
- After placement changes, the owning directory description should state current locations, purposes and any pending cleanup targets or dependencies. Use links from other documents rather than repeating inventories or move/delete histories. Keep an unfinished cleanup recorded until its outcome is verified; a documentation edit does not establish that files were moved or removed. Apply the document governance editing criteria.
- For generated or temporary output, use existing ignored locations. Check ignore rules and staged files; ignoring a path does not untrack already tracked files or guarantee secrets are safe. Do not commit data, weights, credentials or build outputs.
- Review the changed paths and references, run checks appropriate to the affected operation, and follow the repository's focused Git commit rule. When a source, destination, ownership or dependency is uncertain, leave the affected item in place and report the obstacle, impact and evidence or decision needed. A scan is scoped: state exclusions and do not claim the whole tree is clean without evidence.
