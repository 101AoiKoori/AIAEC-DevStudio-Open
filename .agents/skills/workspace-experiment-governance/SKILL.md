# 数据与实验管理

开始涉及数据或指标的实验时自动使用。只读比较已有结果只检查相关来源和指标口径，不重新训练、改数据或写报告。运行已有脚本不自动引发代码重构；编写/修改脚本逻辑才组合 `shared-code-interfaces`，文件产物由 `workspace-file-governance` 管位置。普通模块 import 和纯注释修改不触发数据流程。

## 需求状态标记与设计先行

需求标签和稳定事项 ID 遵循 `docs/PERCEPTION_DEVELOPMENT.md` 的“需求状态与提醒”，写入唯一需求源并同步生成副本。标记已解决时说明是素材具备、策略实施、代码完成还是验收通过，以及直接证据；不把不同阶段合并成一个完成结论。

先用规则、任务目标和可解释逻辑确定需要学习的特征、应打破的依赖及合理状态组合，再查询来源和入口落实方案；不要求实拍证据逐一覆盖逻辑设计出的合成组合。组合保持目标语义、物理可行性及标签正确；证据用于记录真实来源、标签状态、实现能力、测量与实际产出，不能把设计假设或权重说成现场分布。把真实未知项列为 `[未定]`，其余不因没有实验结果而悬置。本轮 V4 依据已有资料与逻辑一次性设计和生产，每模型只有一次训练机会；不把常规开发验证、模型验证或测试设为前置，不以模型验证结果安排重训或选模；用户明确授权的有限测试按其范围执行。出现新需求或逻辑矛盾时记录依据并处理；不得用“还需实验”替代当前可执行设计。

## 标注状态分层

把 `source_available`、`annotated`、`candidate`、`auto_validated`、`human_confirmed`、`training_admitted` 作为独立层分别计数，并同时报告 `pending`；不得把 `human_confirmed=0` 写成没有标注，也不得因缺少人工确认清除候选或既有标注。程序化检查只支持 `auto_validated`，不能填 `human_confirmed`；人工语义确认与框、关键点或掩膜确认分别记录。只有实际失败证据支持 `rejected`/`excluded`，缺少 `accepted_by`、未复核或未准入都保持 pending。复核或 manual 文件重跑必须 merge-preserve，默认校验只读；按模板重建须显式请求、检测非空人工内容并先备份。详细层级和摘要要求见 [数据权威记录](../workspace-doc-governance/references/data-authorities.md)。

## 选择已有实验路径

- 明确本次问题、基线、改变因素、目标数据域和判断标准。先查现有生成器、训练器、审计器、配置和结果，避免另造同功能入口。
- 需求来源是 `config/perception_tasks.json`；数据设计看 `docs/DATASET_DESIGN.md`，当前数据及停用版本看 `datasets/README.md`，再按需读任务研究文档。目录结构以 `config/workspace_layout.yaml` 为源，结构检查用 `python lab/scripts/contracts/workspace_layout.py check`。对象类别、所有者、权威源和版本策略以 `config/workspace_ontology.yaml` 为源，检查用 `python lab/scripts/contracts/workspace_ontology.py --check`。状态目标与组合轴分开记录：`config/task_targets.yaml` 是模型要学习的类别、关键点、OCR 或计数，`config/combination_axes.yaml` 是用于排除或平衡无关噪声的干扰条件；覆盖与容量缺口用 `python lab/scripts/contracts/state_coverage.py` 查看。不要凭文件名中的 latest/final 或日期选数据。
- 将场次/源视频/物料实例、派生样本、split、实验配置、模型及指标关联起来。复用已有 manifest、run_metadata 与日志；代码配置及修订历史统一使用 Git。

## 先核对现有资产

用户指出素材、真值或数据策略已存在时，先检查指定任务目录、现有生成配置及元数据，区分素材身份、类别数量、场景实际计数与人工真值；不能仅因没有找到预设格式的 manifest 就宣称没有数据。已实施的策略写明证据和覆盖范围，缺少效果评估只标记验收待完成。

按选定方向列出假设、来源和已知失败风险；本轮不安排模型验证，未知效果保持未知。训练、颜色扰动、跨帧计数等各自使用符合语义的证据口径；不要把单图检测指标当成整段去重准确率，或把颜色随机化配置当成已证明颜色解耦。

## 数据与指标的决策门

- 核对来源、许可、标注含义、类别/字符/关键点顺序、形状和坐标。负例、漏标、未知和遮挡不可互换；不明标签先标记待核实。
- 按实际需要记录已知来源、场次和样本复用关系。用户允许同源样本用于训练、验证和测试；同视频邻帧和同源派生不能伪装独立采集。路径不重叠、种子不同或文件不同均不能证明来源独立。
- 样本的采集/生成方式与来源谱系分别记录；按[数据来源与生成方式的定义](../../../docs/DATASET_DESIGN.md#数据来源与生成方式的定义)区分直接相机采集、实拍增强、图像处理合成、Blender 渲染及渲染与实拍混合，并记录可交叠的处理步骤和父来源。派生数据保留实拍来源，但不算新的独立采集。分割比例以数据设计和实际条件决定，不固定写死；评估结论说明对应数据类型，不能把一种类型的结果泛化到其他类型。
- 使用 Blender 资产时，记录确切场景/模型路径和版本、父素材、生成代码/配置及参数，并沿用已有 manifest 和来源关系。多次渲染仍属于同一场景来源；模型/相机证据分别注明实测、拟合、近似或未知。换版不改写旧样本的父来源。资产归属见 [数据区说明](../../../datasets/README.md#blender-源资产与派生数据)，设计边界见 [数据集设计](../../../docs/DATASET_DESIGN.md#blender-场景来源与样本谱系)。
- Blender 来源选择前查 `datasets/blender_source_registry.sqlite3` 中的当前分类和已核实关系，并单独确认所需文件在磁盘上存在。历史 manifest 的 `source_blend`、`scene_file` 等字段记录生成时声明的来源路径；没有对应关系证据时，不据此推断精确父子谱系或二进制身份。SQLite 是分类目录快照，不自动监控文件变化。
- Blender 预览或 `editable visual prototype` 状态只说明有可编辑场景/预览记录，不证明模型相对基线有所改善、符合物理实物或已获准生产训练数据；比较须有明确基线、可比条件及实际判据。
- 同一任务存在多个场景分支时，按当前生成器和批次清单分别识别其用途及真值证据；文件较新、能被入口加载或与另一文件逐字节相同，均不足以单独证明其为任务唯一权威或已验收模型。
- 固定比较口径：指标分母、失败/排除样本、各数据源权重、选模标准与基线。更换数据域或过滤样本后不能直接横比旧指标。测试集不用来选模或调参。
- 种子用于记录，不承诺跨设备逐字节重现；记录实际软件/硬件环境、配置与执行命令。不要为了记录复制原始数据进 Git。

## 有界运行和结果维护

- 先检查现有脚本的参数、输出覆盖方式、资源、预计耗时和停止条件。已有适用于当前代码/配置/输入的流程检查可复用；仅在改变或风险需要时做小规模检查，不机械重跑。再按本次授权范围执行，不自动把单次实验扩为无上限搜索。
- 已有输出默认不覆盖；明确授权的重生成须核对准确目标、来源清单和旧结果依赖，并使失效审计/指标明确过期。复核与 manual 文件必须 merge-preserve 既有候选、标注和人工决定；模板重建是单独的显式操作，并须检测非空人工内容、先备份后重建。未获覆盖授权时不添加覆盖参数；已授权时使用必要参数，不重复询问，也不扩大到无关数据、模型和用户资产。覆盖前读取基线配置与指标，将必要比较事实保留在现有研究记录或本次结果中。
- 采用已有结构检查，并按任务做视觉/语义复核。成功返回码和完整文件数不能证明标签正确；抽样复核须说明覆盖范围。
- 记录实际生成/训练/评估数量、失败与排除数、分源指标和资源结果。中断、OOM、空 split、缺失模型、恢复不兼容或清理被拒绝都明确报告；检查活跃进程后再决定重试，避免重复启动。
- 有持久维护价值的结论通过文档 Skill 更新现有任务记录；无合适文档时按文档治理规则决定是否新建，临时或只读问题直接回复即可。数据和权重保持忽略。模型被选择用于正式配置时调用 `workspace-offline-delivery`，单次研究权重不自动进入交付；实验指标不会自动成为实车验收。
- 维护结果时区分当前选用方案、对照实验及停用产物。实验记录保留用于复核的输入、版本、环境、指标和限制；清理过程与纠错对话按文档治理准则删去。产物位置和待清理范围在数据/模型目录说明维护，研究文档引用；重写记录不等于重新运行验证，也不改变旧指标的适用版本。

## 无法完成时

给出“缺失证据或阻碍 → 无法完成的项目 → 结论受限范围 → 下一步所需信息/操作”，继续独立可行的准备工作。将证据与限制合入共同任务结果；公共检查、记录及提交按 AGENTS 执行一次。

用户要求比较方案，或某个关键未知需要对照证据时，执行限定问题、资源与停止条件的比较；设计先行不排除这种实验。`docs/PROJECT_DIRECTION.md` 的理想硬件前提允许独立设计，真实采集和效果结论仍使用实际设备、样本和真值。若反证影响已解决事项，按文档治理规则重开对应状态。
