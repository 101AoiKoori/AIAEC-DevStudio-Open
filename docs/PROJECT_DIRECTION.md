# 项目方向与约定

本文是技术选型与总体架构方向的维护入口，记录确定的开发路线及待验证的候选方案，不代表功能已经实现。具体比赛识别需求以 [`config/perception_tasks.json`](../config/perception_tasks.json) 及其生成文档为准；调度机制以 [异步识别设计](ASYNC_PERCEPTION_DESIGN.md) 为准。算法路线在本文维护，任务规则在配置中维护，其他文档引用对应来源，避免重复维护。

## 分工与目标

当前主线由本工作空间负责**国赛全部识别任务**，包括人物、车牌、红绿灯、指示牌、垃圾桶、火灾、异常温度、仪表和非机动车。导航与移动由协作方负责；识别侧提供场景识别结果、状态、图像证据及终端/播报所需内容，并共同约定观察点、触发条件和结果接口。

比赛规则要求一键启动、自主运行，每轮 5 分钟。应关注有效时间内完成的识别、输出及播报；不能只优化模型单次推理速度而忽略排队、图像保存和总耗时。各任务的分值、输出要求和待裁判确认问题见 [任务总览](../lab/features/README.md) 与 [任务矩阵](TASK_MATRIX.md)。

## 包命名与代码边界

项目自建 ROS 包统一命名为 `aec_<职责>`：`aec` 是本项目使用的简短前缀，职责部分使用简短清晰的小写英文，多个词以单下划线连接。包目录名、`package.xml` 的包名、CMake `project()` 和本包 Python 模块名保持一致，避免依赖导入名和 ROS 包名分叉。

现有包 [`aec_vision`](../ws/src/aec_vision/) 承担共享识别核心。新增包按实际职责决定，并先检查 ROS 环境中的包名和 Python 模块名冲突；外部依赖和厂商包沿用其原名。

`ws/src/` 只放可部署 catkin 包；训练脚本和实验分别位于各任务的 `lab/features/`；数据和模型不提交 Git。独立实验与 ROS 适配层导入 `aec_vision` 内同一份推理核心，不维护第二套识别代码。

正式识别模型直接放在 `ws/src/aec_vision/models/`，采用平铺目录；文件命名与多文件格式约定见[识别开发设计](PERCEPTION_DEVELOPMENT.md#代码与数据的位置)。

## 运行方式与开发环境

- 目标为 Ubuntu 20.04、ROS Noetic 和 Python 3；Windows 进行代码开发与离线检查，实车与 ROS 行为须在目标机验收。
- 小车通过现场隔离网络连接，连接电脑能进入 NoMachine；目前已实际测试可将文件拖入远程会话。联网开发机和连接小车的电脑可分工，代码与样本通过文件交接；小车不要求联网或运行 agent。
- 当前没有可用的国赛仿真地图。场地地图、观察点、路线与设备接口以实车测量为准，不沿用省赛坐标。两条路线和 waypoint 目前只是配置骨架，具体分支由现场禁行牌决定。

## 识别与调度方向

- 对可后台处理的静态任务，优先在观察点采集必要原始帧并交接，然后继续导航；检测、识别、画框、保存、汇总和播报可在后台进行。同一帧可供多个任务使用，是否能共享同一次模型推理取决于模型与场景。
- 不把画质评分作为现场考核或离开条件；只有极短耗时且不影响主进程时才考虑可选后台提示。采样失败、原始数据未接收和写入失败需明确报告。交接延迟与数据保存保障的取舍需实测。
- 红绿灯和禁行牌会影响当前行驶决策，必须及时提供可靠且新鲜的结果；未知或过期不能用于放行。人物等多个场景的结果应按身份汇总，失败不伪装成零。
- 借鉴操作系统的任务状态、优先级、队列和资源隔离思想。模型尽量复用；CPU、内存、磁盘、实时识别与导航之间的竞争、时间预算和并发方式以小车实测决定，不承诺硬实时。
- 设计顺序采用“先依据规则、数据关系和可执行逻辑选定方案，再用实验验证并修正参数或实现缺陷”。不因尚无实验结果而长期停留在并列方案；实验回答既定方案是否实现目标、失败发生在哪一步及需修正什么，不负责替代系统设计决策。新需求、逻辑矛盾、接口约束或数据反证改变关键假设时，重开相关方案选择并记录触发依据。
- 省赛代码、模型与参数是可比较的来源，不直接认定其采样时序、帧数、仲裁、路线或阈值适合国赛。车牌自研 CNN 为现有主识别器，第二 OCR 引擎是可替换组件；PaddleOCR 因依赖和设备适配存在替换风险，双路读取与仲裁契约保持稳定，候选引擎进入纵向选型，不把 PaddleOCR 永久写成不可替换的架构前提。

### 软件设计前提与需求状态

当前阶段以任务逻辑、数据和视觉训练为主。未提供具体限制时，按相机可读清目标、红外设备可用、底盘可执行指定运动的理想硬件条件设计；参数作为接口输入，不反复将硬件未知项列为软件方案阻塞。实际部署遇到明确约束时再调整，不将设计假设描述为实车验证结果。

每个需求的状态在统一任务配置维护：已明确、待解决、待全局规划、未定、已解决（须说明解决范围及证据）。设计确定与实现完成分别表达；状态定义见[需求状态与提醒](PERCEPTION_DEVELOPMENT.md#需求状态与提醒)，由文档治理 Skill 执行同步。路线触发位置、灯控 ROI 激活、扫描区间与模型整体调度属于待全局规划事项，不妨碍各识别核心开发。

### 模型加载时间指标（项目目标，待实测）

用户提出完整系统的模型加载时间**目标约 10～20 秒，硬上限 60 秒**；这是对整套国赛识别方案的预算，不是每个 YOLO 模型各有 60 秒，也不是已经测得的成绩。完整方案应覆盖启用的全部必需模型与两路 OCR；不能只测仪表或通过分批、延迟加载把实际等待藏起来。首版测量口径建议：记录一次完整运行涉及的每次模型加载、初始化和必要预热（包括首次推理触发的延迟初始化）；统计各加载区间的墙钟并集，包含串行切换及重复加载，重叠区间只算一次；另报各模型区间时长之和与端到端启动至可用耗时，避免并发或把加载挪到赛前造成误解。是否计入比赛计时按现场规则确认，不能假定赛前准备时间可用。具体边界和时间戳机制需目标机联调确认。

在目标车的冷启动和常规导航、相机及后台负载下，分别记录各模型与完整方案的加载区间、初始化、首帧预热、模型切换/重载次数、设备内存峰值、从启动到必要功能可用的墙钟时间，以及比赛期间造成门控或后台排队的额外等待。区分系统冷启动、进程重启热缓存和重复加载，固定模型组合、版本、硬件和路线；报告每次及中位数、最慢值，包含失败和超时。测量前明确次数并覆盖两条路线及完整任务组合；超时、内存不足或加载失败标记未达标，不能跳过模型后宣称达标。10～20 秒是优化目标，**超过 60 秒不达该项目指标**；实时灯控与禁行牌及时性和五分钟内识别、图像及播报完成率需单独满足。不得为达时间预算牺牲必要任务或安全门控。测量及调度实施见[异步识别设计](ASYNC_PERCEPTION_DESIGN.md#模型加载计时和资源对照)，当前没有目标车结果。

## 当前可用内容与下一步

### 当前技术路线

以下是开发决策，不更改比赛输出要求。独立训练表示数据、标签与模型可以按任务优化，不表示每个模型必须独占一个常驻进程。所有正式推理仍由 `aec_vision` 共享核心提供。

识别模型以合成数据为主线，现有实拍照片和视频也可参与训练、验证和测试。样本同时记录来源谱系和生成方式，区分相机直接采集、实拍增强、依据实拍拟合的 Blender 渲染、实拍场景合成；实拍拟合渲染保留真实物料特征依据，可用于实拍相关评估并单独报告。实拍素材覆盖楼宇、赛道、垃圾桶、人物、电动车、红绿灯和禁行牌；已有视频背景已作为合成数据基底用于训练。原始媒体和派生图保留已知来源；按用户确定的方案，同源素材可在不同任务及集合复用，评估时说明复用范围。采集批次、覆盖与数据产物见[数据区说明](../datasets/README.md)和[数据集设计](DATASET_DESIGN.md)。红绿灯使用免训练 HSV 方案，红外任务等待硬件数据。

| 红绿灯 | 延续省赛的 OpenCV HSV 与三条可调竖向长条 ROI 方案；在 waypoint 固定角度停车观察，从左到右按红、黄、绿灯位使用对应颜色和亮区判断，短时序稳定确认 | 两处灯位分别标定 ROI 位置、宽度、HSV 阈值和停车位置的允许偏差；漂移、反光、过曝、断流、结果过期输出未知。持续处理最新帧，不能排在视频离线推理之后；不以灯周期推算绿灯 |

| 车牌 | 检测器 + 自研 CNN OCR + 可替换的第二 OCR 引擎；按同一车牌裁剪运行双识别并保留分歧 | 默认纵向设计视频扫描、车辆轨迹关联、分时采样、多帧整牌融合、车位绑定与证据帧选择；PaddleOCR 为当前基线候选并需要评估替换，不因此搁置融合架构 |

仪表优先攻克：围绕单个双针关键点模型和人工刻度映射建立一条完整单帧识别链；现有纯 OpenCV 结果保留为既有实验记录。输出标注图需圈出温湿度两组的每个刻度，并标明两根指针及其原点；准确坐标和映射以实物标定为准。

### 采样模式：单帧、短序列与扫描视频并存

全系统统一规划原始数据复用与模型调度：在覆盖和时效满足各任务时共享一次采集；不同模型串行、有限并行或混合执行待整轮资源与时限实测决定，具体比较见[异步识别与资源调度](ASYNC_PERCEPTION_DESIGN.md#全局原始数据复用与模型调度)。

每项观察由逻辑设计指定采样模式；需跨位置覆盖和去重的车牌、电动车采用有界平移扫描，红绿灯持续观察最新帧，其他静态任务采集一帧或有限短序列后后台处理。先定义扫描起止、观测身份、状态保留与计数提交规则，再用数据验证覆盖和关联；不等待实验来决定是否需要一套连贯的扫描状态机。视频采集帧率与模型推理帧率分开，整段源视频写入存储，后台流式解码，不将完整视频帧常驻内存。

**车牌扫描**：导航与感知共享扫描段身份，运动中连续采集并保存带单调时间戳的视频；感知按固定时间/位移间隔抽帧，以车牌检测框和跨帧关联维护车辆轨迹。同一轨迹进入车位观测区后建立候选车位关系，追踪器关联允许断续，不按帧直接加票。对轨迹内 OCR 运行结果按完整字符串候选聚合，CNN 与第二 OCR 的输出、分歧和原帧引用都保留。车辆离开扫描段或到达明确截止点时提交该轨迹的车位结果及支持帧；车位归属冲突时保留待定，禁止按出现顺序填车位。第二 OCR 可替换，替换不改变检测、轨迹、融合和车位绑定接口。

**电动车扫描**：采用单向、已定义覆盖范围的扫描段，记录相机/底盘运动与时间，YOLO 在受限采样帧检测车辆，车辆级跟踪状态跨抽帧和视频片段延续。每轨迹维护首末时间、观测区域、框/外观摘要、正常/倒伏证据、关联状态和是否已计数；重复检测更新已有轨迹，遮挡后由运动连续性、外观和场景位置重连，歧义目标进入暂存集合，不立即重复计数。车辆离开区域/扫描终点后按轨迹汇总姿态并提交一次区域计数；扫描结束用区域覆盖状态检查漏项，重扫通过原观察身份合并，不建立新计数批次。A/B 街分别输出违停有无，任意姿态的电动车均表明该街存在违停；停车区输出车辆总数及倒伏数，姿态不明时倒伏数不能伪装成已确认。首版轨迹关联采用 BoT-SORT 的相机运动补偿方案，但其 ID 是内部标识，计数语义由本状态流程定义。

片段边界延续同一扫描上下文。运行中断则将扫描记为部分完成；重新观察必须明确与已有实体的关联，已提交车辆不重复累计。若返回重扫，先将新轨迹与扫描已有实体做关联或标注歧义，不直接再加一次。跟踪丢失时结合扫描路径与轨迹末次位置做短时关联，超过关联窗口则进入暂失集合；仅在明确离开边界或扫描闭合后提交；随后出现但无法确认是否为旧目标的车辆进入歧义计数，不默认为新车。终点覆盖检查使计数完整性可审计。遮挡视野中的目标需要通过扫描角度和侧向移动减少盲区；逻辑无法补出始终不可见的物体。

扫描是车牌和电动车的设计主流程。实测用于验证各状态转换和失败恢复，优化抽帧间隔、关联窗口、模型资源与速度；若具体观测暴露缺陷，修正该环节，不把整套方向退回到“是否扫描”的空泛选择。采集时保留完整原始视频，算法按有界帧率抽样，后台流式解码。姿态/号码决策来自轨迹融合，完成覆盖和截止处理后才提交区域结果。画质检查不增加主流程等待条件。

### 分级状态机与资源生命周期

采用分层决策、模块状态归属和统一资源准入，在同一小车上实现一个协调器和少量执行器。

- 比赛层管理本轮、路线分支、总截止时间与收尾；观察层管理到点采样或扫描区间；识别作业层管理排队、推理、融合、证据和输出。导航状态与后台识别并行，只有门控任务或数据交接失败才按策略影响行驶。
- 采集结束、原始数据交接完成、推理完成、证据就绪和播报完成是不同事件。一个父任务按必要子任务的完成条件收敛，不能要求所有后台作业结束才进入下一个观察点。
- 协调器统一限制内存、模型并发、视频写入量、磁盘余量和队列容量；执行器负责释放自身图像、张量与模型引用，存储组件负责文件生命周期。每项资源只有一个负责释放的所有者，其他消费者登记使用关系。
- 模型按路线需求异步提前加载、预热和有限驻留，后期任务的模型不要求在启动阶段全部加载；应在任务需要推理前准备就绪。模型切换要计入时延，不因每个事件重新启动模型。导航和实时灯控预留能力，后台加载与推理不能挤占到控制失效；未及时就绪时按任务门控或后台截止策略处理。
- 原始帧/视频、裁剪中间件、最终证据和结果分别定义保留策略。中间件在全部消费者结束后可释放；本轮必要原始数据与证据不得因内存压力提前删除。临时资源回收、结束保留及新一轮重置分开处理，详见异步设计。

配置职责保持分离：需求配置只描述规则；现有 `competition.json` 管任务开关和路线选择。采样模式、扫描起止、模型选择、融合阈值、截止时间及资源配额将由运行配置统一引用，尚未新增这些可执行字段，不能将本文方案理解为配置已生效。每轮启动固定配置版本，切换路线或重置须产生新的运行/扫描身份，防止旧消息污染新任务。

### 技术依据与适用范围

本轮查阅的 [Ultralytics 分类说明](https://docs.ultralytics.com/tasks/classify/) 将分类定义为整图类别预测；因此人物计数选择带类别的检测输出。[跟踪说明](https://docs.ultralytics.com/modes/track/) 及 [BoT-SORT 官方配置](https://github.com/ultralytics/ultralytics/blob/main/ultralytics/cfg/trackers/botsort.yaml) 提供跨帧关联及相机运动补偿能力，是当前扫描主线的技术依据，不保证本场景准确率。移动相机下的去重、扫描分区和多帧 OCR 融合属于本项目设计推断，须实测。

这些网页描述的是当前上游实现，不表示其最新版本可直接用于 Ubuntu 20.04 / Python 3.8。目标机须固定兼容的 YOLOv8、推理框架、OpenCV 和跟踪器版本，并离线准备依赖与模型；不能未经验证升级部署环境。

### 实施顺序与验收

已建立九项任务实验区、需求文档生成器、任务开关与路线配置读取组件、车牌双 OCR 与 CNN 训练入口，以及仪表几何实验。车牌验证范围见[卡通验证回归](research/PLATE_DUAL_OCR.md#卡通合成验证集回归2026-11-07)及[结构对照训练](research/PLATE_DUAL_OCR.md#cnn-结构对照训练2026-11-06)。ROS 构建、实车传感器、各任务准确率及并发时延均待验收；任务开关和路线配置尚未接入真实调度或导航。

九个检测／关键点模型的工作空间训练入口和配置位于各任务 `training/scripts/`、`training/config/`，共用引擎位于 `lab/training_common/`。数据准备已具备本轮训练输入；V1/V2 作为真实低预算试验，V3 作为当前完整训练配置，在分发电脑运行。`training_packages/` 仅是 V3 的额外分发镜像，Windows 独立依赖也由 lab 中的构建工具生成。数据来源见[数据区说明](../datasets/README.md)，入口、版本比较和回传见[训练流程](TRAINING_WORKFLOW.md)。

下一阶段重点是开展首轮训练与基线评估，并按评估结果核对实物一致性和标注；同时补齐识别链：楼名纸条与车牌 YOLO 包只定位，文字读取仍需 OCR；仪表八点不直接提供逐刻度读数；人物/电动车的跨帧计数、火焰归属、垃圾模型接入和路线门控尚未形成完整任务链。红外设备与热异常数据未到，无法标定与验证楼层热异常；其余任务可继续推进。

优先用已有国赛照片和完整视频核对各任务的合成数据，按用户确定的同源复用方案使用工作空间训练配置，记录评估范围，推进合成训练、各识别任务基线、统一调度及终端/图片/播报输出。红外热异常所需设备数据和逐层温度真值按实际缺口记录；接口、资源限制和五分钟内的完成率按实际测量定稿。未采集或未验证的项目如实记录，不将设计或离线结果写成实车结果。

### 原文、确认与推导的边界

- 第 11 页要求四桶分别判断开闭、垃圾类别、投放正确与否并框选；实物右图标出正面垃圾贴位置。用户进一步明确：只需观察所有垃圾桶正面，不需要看桶内。关闭状态下仍要执行垃圾贴识别。
- 第 12 页提供四类共 24 个垃圾图例。它们可以作为初始标签和映射依据，但原文没有明确承诺现场图案集合完全封闭。不能把未知图案强行归为已知类别。
- 第 7 页给出物料朝向与约 60 cm 主通道；垃圾桶在楼宇 C 附近、中央道路一侧，朝向图示右侧，与右侧停车场之间的观察通道相关。地图中的空间邻近不意味着一个相机视角能同时看清所有目标。
- 用户提供了实地场景俯视照片与布局示意图，并说明实景转向后与示意图的楼宇编号及物料位置一一对应；这是识别采集和场景归属的参考，详见[数据集设计](DATASET_DESIGN.md#场景证据与楼宇采集)。照片和示意图不能替代比赛现场的地图、路线坐标、观察姿态及设备标定。
- 第 8 页两条红线的中央路段走法不同，禁行牌决定路线；第 19 页给出路线二的真实布置。每条路线须分别安排面向桶正面的观察机会，不能假定同一 waypoint、车身朝向或任务触发顺序适用于两条路线。物料朝向以第 7 页橙黄色箭头核对，不能仅凭实景照片透视确定全局朝向。
- 右侧车位和电动车停车区沿通道分布，为连续观察提供研究动机；图示未证明平移所需净空、相机视野、运动权限与全部覆盖条件。扫描轨迹必须落在允许路线内，不能为了看正面自行穿越限制区域；红绿灯仍需等待线前停车。

### 垃圾桶识别如何拆解

第一版使用 OpenCV 判断已定位桶体的颜色，独立 YOLO 模型分别识别正面垃圾贴和桶盖开闭，再按规则映射判断投放。四桶分别记录有效状态，部分失败不抹去其他有效结果。颜色、关联和规则判定核心已建立；定位、两项模型与整链仍需开发和现场验证。完整流程见[垃圾桶识别方案](research/OPEN_SOURCE_METHODS.md#waste_bin)。

### 平移与旋转协同的观察轨迹

小车支持同时平移和旋转。导航与识别共同规划车体路径及相机朝向变化，在允许通道内逐渐转向任务物料；平滑程度与可用扫描速度需实车测量。

观察段除起止位置外，还应表达目标区域、期望朝向变化、采集启停及时间关联。相机固定安装时，车身朝向影响相机朝向，需要使用安装外参；车体速度的坐标系与导航输出约定必须明确。底盘具备该能力不等于当前 move_base 局部规划器已正确启用全向速度与同步转动，需导航方检查配置和接口，识别节点不另行发布运动指令与导航争抢控制。

约 60 cm 通道内要计算旋转时整个车体的扫掠范围，并限制速度、角速度及加速度；同时保证物料在相机视野内的有效观测时长。平移加转动可能改善取景，也可能引入模糊、视角变化与更复杂的跨帧关联。先使用固定目标的短观察段验证路径跟随、视野覆盖和保存能力，再接入车牌、电动车扫描与垃圾桶正面采样。灯控停车和禁行分支优先于连续扫描。
